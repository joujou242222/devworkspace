## V08 database and object backup/restore

The successful cold snapshot is `snapshot-2026-10-19T103138153Z` under ignored `.local/phase9`. The recovery tool measured headroom first, stopped only owned API/worker/proxy and native processes, copied the retained PostgreSQL data directory and SeaweedFS files, and verified the copies. The snapshot contains 659,864,660 PostgreSQL bytes and 2,744,557 SeaweedFS bytes (662,609,217 bytes total). At preflight C: had 11.36 GB free and D: had 51.80 GB free; the planned D: requirement was 1.46 GB including reserve. Source PostgreSQL was stopped gracefully in 214 ms, and the original data directories were never replaced.

The restore created separate PostgreSQL and SeaweedFS copies in `restore-2026-10-19T103138153Z-7da3f95d`, using alternate local ports and paths. It verified copy hashes before startup, all 51 databases and 65 public-table row counts, all 43 applied migration digests, 51 enabled/forced-RLS tables and zero unvalidated constraints. PostgreSQL graceful restart retained row counts. The restored database retained 212 deliverable versions, 221 review cycles, 68 decisions, 109 feedback threads, 7,387 audit events, 7,415 outbox events, 22,144 consumer receipts and 3,148 notifications. These are restore identity/count checks, not a substitute for cryptographic tamper-proof audit storage. `pg_amcheck.exe` was not present in the pinned portable PostgreSQL distribution, so that check was not run.

The cold object copy reconciled 618 canonical storage versions (602 keys, 184,794 bytes read) against 586 database-pinned references. Every reference matched its exact key, S3 version ID, digest and size; there were zero missing, mismatched or conflicting references and zero delete markers. Thirty-two versions in 16 keys were unreferenced. The staging copy contained 284 versions/keys (49,133 bytes read), zero unknown keys, zero lingering cleanup tombstones and one active/pending intent. The reconciler emitted only truncated key hashes. No canonical object was removed.

After the complete final browser and API regression sweep, a second read-only source reconciliation at 11:27 UTC found 676 canonical versions across 659 keys (199,196 bytes read) and 642/642 exact database references matched, with zero missing, mismatched or conflicting references and zero delete markers. It found 34 unreferenced versions in 17 keys. Staging had 311 versions/keys (53,159 bytes read), zero unknown keys and cleanup tombstones, and one active/pending intent. Relative to the snapshot point this is a net increase of two unreferenced versions and one key. Provenance had not been established at that observation time; the later targeted inspection below explains the increase. Every object was retained for operator review. This 11:27 UTC result is historical; the targeted inspection records the later working-store status.

The later targeted read-only inspection at 20:01:41 UTC confirmed 676/659 canonical inventory and 642/642 exact references, with 34/17 unreferenced versions/keys. It matched 17 40-byte versions to the Phase 4 test’s deliberate latest-pointer overwrite payload and 14 95-byte versions to the test’s direct publication of its exact 95-byte image fixture. The 17 overwrites are under keys with valid DB-pinned versions; 14 of them are newer than those pinned versions. One 30-byte version has no provenance, and two 95-byte original/preview versions match a FAILED five-attempt upload without a job, asset, or recorded processing steps; these three remain unresolved. The +2-version/+1-key difference from the cold snapshot is explained by one new direct-publication probe and one new latest-pointer overwrite. See the per-object sanitized table in the closure report.

The same inspection found 308 staging versions/keys, zero unknown keys, zero cleanup tombstones, and three `ISSUED` rows whose five-minute capabilities had expired. No row had a staging object, job, lease, asset, or cleanup record; none had reached the SQL cleanup threshold of `expires_at + 24 hours`. The earlier 311/one-object aggregate did not retain enough identity to prove which object disappeared. No object or row was changed during this follow-up.

In the isolated clone, a disposable bucket accepted two versioned writes; exact-version reads matched both byte digests and the latest read matched v2. A wrong pinned version and a deliberately missing disposable object were detected. The disposable test did not modify source data. A cloned storage process interruption followed by graceful restart recovered, after which reconciliation still matched. The tool stopped its clone processes and verified the original database/storage reconciliation and native services were restored.

The snapshot has a quiesced-writer boundary but does **not** claim an atomic PostgreSQL/S3 transaction snapshot. Its physical copies are unencrypted and include private tenant content. `.env.local`, S3/storage credentials, TLS keys and the mail encryption key remain outside the snapshot. The mail key in ignored `.local/phase2-credentials.json` is required to read pending encrypted mail. Protect backup files and private credentials separately; do not transfer this snapshot to another machine without an approved encrypted backup/key-custody process. There is no automatic retention or purge job for snapshot/restore copies.

## Bounded workload and responsiveness

`pnpm phase9:workload` retained a synthetic tenant with 10 projects, 100 tasks, 100 milestones and 1,000 structured documents; API concurrency was capped at 4. It ran in 18.1 s. The figures below are local Windows observations, not a production SLA or cloud capacity estimate. The listed thresholds are diagnostic guardrails for this bounded local run only.

The task page `EXPLAIN ANALYZE` planned in 3.23 ms, executed in 0.129 ms and hit 84 shared buffers. The authorized scoped document query read/sorted all 1,000 rows before application cursor slicing; it planned in 1.364 ms, executed in 0.662 ms and hit 984 shared buffers. This is a boundedness/memory concern at larger tenancy, but current API p95 is 53.45 ms against a local diagnostic target of 750 ms, and query execution is below 1 ms at this size. A keyset/SQL pagination rewrite was therefore deferred pending a larger justified workload and a proof that total counts, ordering, authorization-before-pagination and ID cursor contracts remain unchanged.

Across four owned Node server processes, total RSS rose from 432,857,088 bytes to 566,394,880 bytes during the run (delta 133,537,792 bytes). A separate run after the 1,000-row expansion showed 384,192,512 to 559,734,784 bytes; results are retained as repeated observations. The first 1,000-document run recorded 104 durable tenant deliveries, with 100 completed at its initial cutoff; the later measured set recorded 108. The post-regression poll confirmed all 108 completed with no pending deliveries and 108 notifications. The earlier completed sample's p95 lag was 5.10 s; after full regressions and interruption tests, the final set's p95 was 54.59 s. The increase is observed but its source is not isolated. No separate file-processing throughput or long-duration 16-GiB stress certification was performed.
