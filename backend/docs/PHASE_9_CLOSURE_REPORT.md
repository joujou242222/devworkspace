## Backup, restore, and encryption

The prior Phase 9 cold snapshot/restore remains the only full V08 rehearsal. It copied 659,864,660 PostgreSQL bytes plus 2,744,557 SeaweedFS bytes into a new isolated restore path and verified 51 databases, 65 public-table counts, 43 migration digests, 51 forced-RLS tables, zero unvalidated constraints, exact object-version reads, and wrong/missing version detection in the clone. That snapshot captured 586 pinned references at its earlier boundary; it is not a restore of the later 642-reference source state. It contains the whole physical PostgreSQL cluster (51 databases, including unrelated databases), so it is broader than an approved product backup.

The existing snapshot and restore copies are unencrypted at the file/archive layer and contain private tenant data. `cipher /c` marked the manifest file `U` (not EFS-encrypted). Its inherited NTFS ACL grants `Authenticated Users` Modify and `Users` Read/Execute, in addition to Administrators and SYSTEM; the Node `0600` manifest creation mode did not narrow those inherited Windows ACLs. `manage-bde -status D:` could not access the required resource, and the BitLocker query reported access denied/no associated BitLocker volume, so host-volume encryption could not be confirmed. Treat the existing copies as locally readable private data; they were not changed, transferred, or deleted.

Recommended repeatable procedure, pending approval of the encryption/key choice:

1. Stop only owned API, worker, proxy, and storage writers; drain database transactions and worker/outbox leases. Wait for the maximum five-minute signed staging capability to expire, then verify no active upload/job lease or storage write. Record this as the quiesced-writer boundary. Do not call the two store copies atomic; the boundary is established operationally by stopping writers.
2. Use a database-scoped backup for only `devworkspace_phase2` (for example, a custom-format `pg_dump` with owner/ACL handling documented); recreate only reviewed runtime roles and grants from the product bootstrap. Do not use a full-cluster dump or include unrelated databases. The current pinned PostgreSQL bundle and PATH have no `pg_dump.exe`/`pg_restore.exe`, so this logical path needs a separately approved pinned utility before it can be executed.
3. Preserve SeaweedFS S3 version identity by cold-copying the complete owned Seaweed data directory and matching binary/config while writers are stopped. The previous isolated physical copy retained exact version reads. A logical re-upload to another bucket would mint different storage-version IDs and cannot be substituted under current immutable database references without an independently authorized remapping design.
4. Build a relative-path manifest with byte counts and SHA-256 hashes, then encrypt the resulting backup plus manifest before it leaves the protected workspace. Sign the manifest with a separately held signing key. Keep the encryption key, database credentials, S3 credentials, TLS material, and mail-encryption key outside the backup and deliver them through separately controlled custody.
5. Restore only into newly created owned directories and alternate loopback ports. Verify the manifest before startup, restore the selected database and exact Seaweed data, run migrations/constraint/RLS checks, then reconcile every pinned key/version/digest/size and review/audit/outbox links. Never point the restore at the source paths.

No encryption utility is available on PATH or in the checked pinned tool paths. An in-memory Node AES-256-GCM check passed synthetic round-trip and modified-tag rejection; it wrote no file and persisted no key, so it does **not** prove backup encryption or key recovery. Operator key-custody alternatives are:

- **Recommended for cross-machine recovery:** an offline asymmetric recipient key (such as age); the recipient private key remains offline and separate. The age utility/key is not installed here, so adoption requires a separately authorized pinned tool and key provisioning.
- **Built-in Node option:** scrypt-derived AES-256-GCM with a high-entropy passphrase stored separately in an approved password manager. Cross-machine restore is possible, but recovery depends on passphrase custody, rotation, and an explicit process for preserving the KDF parameters.
- **Windows DPAPI:** simplest same-user/same-machine protection, but it does not meet cross-machine recovery unless a separate exportable key scheme is designed; it is not the recommendation for V08.

Proposed retention for operator review is seven daily, four weekly, and twelve monthly encrypted recovery points, with at least one encrypted copy on a separate machine/location and a periodic isolated restore. No retention schedule or purge automation is active. Do not remove any current copy to make room for this proposal.

## Notification delivery latency

The earlier bounded run initially had 100 of 108 task-event deliveries complete, with p95 5,147 ms; its later drain had 108/108 complete, zero pending, and p95 54,590.155 ms. A read-only query against the retained fixture confirmed 100 workload tasks, 108 delivery rows, 108 completed deliveries and receipts, all at one claim attempt. Event-to-first-receipt p95 was 54,589 ms; event-to-delivery-completion p50 was 3,325 ms, p95 54,590 ms, and max 55,505 ms. There were no retried rows in that sample.

The schema cannot split that tail into outbox claim, Redis enqueue, worker wait, projection, or PostgreSQL lock time: the retained row has attempts/lease/available/completed fields, but no historical claim time, queue-accept time, worker-start time, or per-stage completion time. In particular, `available_at` is updated by the finish/retry function after each attempt, including successful completion, so it is not a historical queue-arrival timestamp. The consumer receipt is committed with delivery completion, so its timestamp is not an independent materialization-stage timer. Current database rows cannot reconstruct the lost stage timings.

The bounded task lock test did observe four PostgreSQL lock waiters, but it is not linked to the delivery cohort. The 54.59-second p95 occurred across an extended regression/recovery interval with concurrent activity; the available evidence cannot attribute it to lock contention, Redis dispatch, scheduling, native resource contention, retries, or materialization. It is not a measured SLA and is not claimed fixed. A future isolated diagnostic should add stage timestamps/metrics and run the same bounded workload against a disposable cloned database and storage, without flushing durable queues.
